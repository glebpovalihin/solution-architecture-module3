# Паспорт инициативы: Извлекать финансовые показатели из неструктурированных бухгалтерских документов и банковских выписок

## 1. Триаж

- **Вход -> выход:** пакет документов -> структурированные поля
- **Какое действие изменится:** предзаполнение карточки заявки вместо ручного разбора
- **Где именно ML / чем закрыть остальное:** OCR модель; валидация (баланс, ИНН, кросс-проверки) и запись - код; подтверждение - специалист
- **Чего не хватает / допущения:** связки "документ -> подтвержденные поля" исторически не накапливались, потребуется пилот
- **Вердикт:** гибрид

## 2. Постановка

Извлечение полей (выручка, прибыль, активы/пассивы, обороты по счетам) из разнородных документов заявки. Выход модели - JSON полей + ссылка на фрагмент-источник + уверенность по полю; бизнес-выход - предзаполненная карточка заявки, подтверждение андеррайтером.

- **Бизнес-цель:** предзаполнение карточки кредитной заявки вместо ручного разбора пакета документов
- **Объект решения:** отдельный документ из пакета документов, детализация до полей докуметнов
- **Входные данные:** несколько видов данных - Excel, PDF-сканы, фото с телефона, выгрузки бухгалтерских систем (текст + таблицы + изображения).
- **Операция:** извлечь сведения - структурированные финансовые показатели  из неструктурированного документа
- **Результат модели:** список полей в JSON: значение + ссылка на фрагмент-источник
- **Результат для бизнеса:** предзаполненная карточка заявки на основе детерминированных валидаций, фильтрации полей без источника
- **Дальнейшее действие:** сотрудник проверяет карточки, правит ошибки и подтверждает - дальше заявка идет по стандартному кредитному процессу.
- **Источник правильного ответа:** подтвержденные сотрудником значения полей + детерминированные проверки. Исторической связки "документ -> подтвержденные поля" нет - накапливается с первого дня пилота.
- **Роль правил и человека:** правила - прием пакета, классификация типа документа, валидация и запись в заявку; человек - подтверждение каждой заявки (решения по кредиту принимает сотрудник); модель - только извлечение полей.
- **Открытые вопросы и предположения:** допустимость обработки документов с банковской тайной и ПДн поручителей требует оценки DPO; доля полей, присутствующих в документах явно

## 3. Качество

- Бизнес-метрика: время разбора пакета (сейчас примерно полтора часа, цель менее 40 мин), доля автозаполненных полей
- Метрика модели: точность по полям exact match после нормализации >= 90 % на читаемых сканах, >= 80 % на фото; полей без источника = 0
- Рабочая точка: поле с уверенностью ниже порога подсвечивается сотруднику.

### Шортлист моделей и процедура выбора

- Жесткое ограничение до шортлиста: лицензия open-weight модели должна допускать коммерческое использование
- Кандидаты: open-weight LLM self-hosted в своем облаке с допустимой лицензией; managed API LLM в выделенном контуре с закреплением версии и отключаемым хранением (пилот); пайплайн классификация страницы -> NER в NLP
- Жесткие ограничения: каждое поле со ссылкой на фрагмент-источник, JSON-схема валидируется, арифметика баланса проверяется кодом - модель без подтверждения источником отклоняется.
- Приемочный набор: 100 реальных пакетов заявок (все типы: Excel, скан, фото), эталон - подтвержденные сотрудником значения
- Метрики: точность извлечения по полям (exact match после нормализации) >= 90 % на читаемых сканах, >= 80 % на фото; доля полей без источника = 0
- Провал: точность ниже ожидаемых метрик - усиление OCR-звена.

## 4. Данные

| Поле | |
|---|---|
| Решение | Данные должны поддерживать предзаполнение карточки кредитной заявки - извлечение финпоказателей из пакета документов |
| Объект и гранулярность | Отдельный документ пакета заявки,поля документа |
| Источник и владелец | Пакеты документов заявок из кредитного пайплайна; владелец - департамент рисков |
| Сигнал / источник правильного ответа | Значения полей подтвержденные сотрудником при разборе, сигналом является факт обработки |
| Доступность признаков после запуска | Документ доступен целиком в момент ответа модели, ограничений нет |
| Разметка | Исторической нет, требуется накапливать с первого дня пилота через проверки: исправление сотрудника = метка |
| Смещение отбора | метки проставляются согласно потоку фин документов, есть риск перекоса в определенные сегменты |
| Репрезентативность | Должны быть представлены все форматы потока (Excel, PDF-сканы, фото, выгрузки бухгалтерии) |
| Объем | Поток заявок x пакет документов, историчские данные отсутствуют |
| Качество | Высокая вариативность форматов, часть сканов и фото могут быть низкого качества |
| Право на использование | Банковская тайна, ПДн поручителей/физлиц, допустимость выделенного контура провайдера для пилота, обезличивание и хранение требует обсуждения с DPO |
| Разрыв и план его устранения | Нет исторической разметки полей. Потрбуется производство эталона в пилоте через подтверждение сотрудником, отвечает дирекция рисков, срок старта - с первого дня пилота |

Вердикт: Pilot-ready - недостаток разметки устраняется параллельно в процессе работы. Приемочный набор - 100 пакетов всех типов.

## 5. Эксперимент

- Офлайн-приемка на 100 пакетах против эталона сотрудника.
- Пилот на 1 кредитном продукте 8 недель: сотрудник работает с предзаполненной карточкой, замер времени и доли правок.
- Успех: время пакета <= 40 мин, точность по полям больше порогов, доля полей, требующих правки меньше 30 %
