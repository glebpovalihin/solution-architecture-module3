# ADR-002. Прогнозировать нагрузку на кол-центр для планирования смен

Версия: v0.1

## Контекст

Кол-центр работает по сменному расписанию, которое на данынй момент составляется по факту и опыту руководителя.
Перерасход ФОТ в простое и недобор штата в пике - прямые издержки, срыв SLA ответа.
Логи телефонии пишут почасовую историю звонков за 1-2 года.
Инициатива: прогноз нагрузки на горизонт 2-4 недели для составления сменного расписания, утверждаемого человеком.

## Жесткие ограничения

1. Данные - агрегированные метаданные без содержания разговоров, записи звонков в модели не используются (ПДн и согласия клиентов не затрагиваются)
2. Прогноз должен быть готов к моменту утверждения расписания - пакетный расчет, не влияет на клиентский путь
3. Логи не должны покидать контур банка без необходимости, внешние API не имеют преимуществ и создают зависимость от вендора

## Рассмотренные варианты размещения

| Вариант | Вердикт | Причина |
|---|---|---|
| Публичный API провайдера | Отклонен | Табличный прогноз ряда не требует внешней LLM; передача логов наружу неоправданна, зависимость от вендора без выигрыша |
| Выделенный контур провайдера | Отклонен | Избыточен: данные не чувствительны к такому уровню защиты, а премия за контур не окупается |
| On-premise | Отклонен для пилота | Данные агрегированы и не содержат ПДн, поэтому барьера нет; CPU нагрузка невелика, on-prem избыточен до подтверждения ценности |
| Self-hosting в облачном контуре банка | Выбран | Модель собственная, стек open-source, CPU достаточно; пилот и прод совпадают - стоимость проверки гипотезы низкая |

## Решение

**Данные:** источник правильного ответа это фактическая нагрузка из логов телефонии, эталон записывается системой автоматически, ручная разметка не требуется.
Вердикт готовности - Ready.
Единственное искажение - потерянные вызовы в перегрузке занижают спрос

**Размещение:** self-hosting в облачном контуре банка, CPU-контур., пилот и прод совпадают

**Модель:** LightGBM на календарных и лаговых признаках (час, день недели, праздники, дни выплат и налоговых платежей, доля потерянных вызовов)

**Процедура проверки шортлиста:**
- Приемочный набор: последние 8 недель истории как отложенный холдаут + стресс периоды отдельным срезом
- Метрика: недобор/перебор смен/сотрудников <= 10% в 90 % интервалов
- Порог из цены ошибок:  недобор в пиковые часы дороже простоя,  планирование по верхней границе прогнозного интервала в пиках
- Провал на сценарии: систематический провал на праздниках -> отдельный режим прогноза аномальных дней, а не калибровка общей модели

## Последствия решения

Положительные: нет вендорной зависимости и платы за запросы, прогноз объясним
Отрицательные: ответственность за эксплуатацию и обновление модели на команде банка, при запуске новых каналов (чаты, почта) модель потребует дообучения

## Допущения

1. Почасовые логи телефонии полные и доступны за 1, 2 года
2. Смежные каналы не входят в проект
3. Ставка сотрудника кол центра для перевода ошибки прогноза в деньги не требуется для приемки - решение принимается по метрике недобора и перебора штата

## Риски

| Риск | Митигация |
|---|---|
| Потерянные вызовы занижают спрос в перегрузке | Признак доли потерянных вызовов, планирование по верхней границе в пиках |
| Смена сезонных паттернов| Мониторинг отклонения факта от прогноза, переобучение по расписанию |
| Модель не будет лучше текущего ручного подхода | Бектест на 8 неделях против текущего механизма, если результат будет провальным, то решение требует пересмотра |

## Триггеры пересмотра

1. Запуск нового канала обращений или смена клиентской базы -> внеплановое переобучение
2. Отклонение факта от прогноза выше порога два периода подряд -> пересмотр признаков и горизонта

## План выхода от вендора

Внешнего вендора нет: модель собственная на open-source стеке, данные внутри контура банка. Зависимость только от облачного IaaS-провайдера; перенос прогноза на другой контур не требует пересогласования договоров обработки данных
