# ADR-003. Извлекать финансовые показатели из неструктурированных бухгалтерских документов и банковских выписок

Версия: v0.1.

## Контекст

Разбор пакета документов кредитной заявки (бухгалтерская отчетность, банковские выписки) занимает у сотрудника примерно полтора часа.
Задача: предзаполнять карточку заявки извлеченными полями, сотрудник проверяет и подтверждает.
Исторической связки "документ -> подтвержденные поля" нет: эталон накапливается с первого дня пилота (исправление сотрудника = метка)

## Жесткие ограничения

1. Банковская тайна и ПДн поручителей: документы не покидают контур банка без договора с обработчиком и одобрения DPO; для пилота в контуре провайдера требуется договор обработки, окончательную допустимость подтверждает DPO.
2. Лицензия open-weight моделей должна допускать коммерческое использование.
3. Каждое извлеченное поле - со ссылкой на фрагмент-источник; поле без источника не попадает в карточку. Арифметика (баланс, суммы) проверяется детерминированным кодом.
4. Модель только извлекает поля; подтверждение и решение по кредиту остается за сотрудником.

## Рассмотренные варианты

| Вариант | Вердикт | Причина |
|---|---|---|
| Публичный API провайдера (multi-tenant) | Отклонен | Жесткое ограничение: банковская тайна и ПДн не могут передаваться в публичный контур |
| Managed API LLM в выделенном контуре провайдера | Выбран для пилота | Быстрая проверка ценности без GPU-инфраструктуры |
| Self-hosted open-weight LLM в облачном контуре банка | Выбран как целевой прод | Полный контроль данных; лицензия с коммерческим использованием; эксплуатация на команде банка |
| Пайплайн "классификация страницы -> NER" | Резерв | Дешевле на больших объемах, но дороже в разработке и слабее на разнородных форматах; вернуться, если LLM не удержит метрики |

## Решение

**Данные:** эталона нет, вердикт - Pilot-ready: производство эталона запускается с первого дня пилота через подтверждение/исправление сотрудником, отвечает дирекция рисков.
Приемочный набор 100 реальных пакетов всех типов, эталон - подтвержденные сотрудником значения

**Размещение:**
- Пилот: managed API LLM в выделенном контуре провайдера. Фиксируются до подписания договора - запрет обучения на запросах, срок и регион хранения, версия модели, SLA. Обезличивание перед отправкой (маскирование ФИО/ИНН физлиц) - только после одобрения DPO.
- Прод: self-hosted open-weight LLM в облачном контуре банка после подтверждения ценности на пилоте и целевых метриках

**Модель:** конвейер "локальный OCR один раз (скан/фото -> текст + layout) -> LLM-извлечение полей по JSON-схеме -> детерминированная валидация". OCR тоже ML-звено, выбирается отдельно (кандидат open-source OCR). Кандидаты LLM: open-weight с допустимой лицензией (прод), managed LLM с закрепленной версией (пилот).

**Процедура проверки шортлиста:**
- Диагностический набор: 12-20 обезличенных документов разного качества и полноты заполнения, просьба о поле которого нет (проверка галлюцинаций). Смотреть на провалы, а не на среднее.
- Приемочный набор: 100 реальных пакетов всех типов, эталон - подтвержденные сотрудником значения
- Метрики: точность exact match после нормализации >= 90 % на читаемых сканах, >= 80 % на фото; доля полей без источника = 0; доля галлюцинированных полей = 0
- Провал на сценарии: низкая точность на плохих сканах -> усиление OCR-звена; галлюцинации -> ужесточение схемы и проверок, смена модели
- Смена решения: точность ниже порогов на приемочном наборе -> пересмотр варианта

## Последствия решения

Положительные: ценность проверяется дешево без GPU, банк не платит за инфраструктуру до подтверждения гипотезы, разметка накапливается с первого дня пилота.
Отрицательные: договорная работа с провайдером и одобрение DPO до пилота, для прода потребуется GPU-контур и команда эксплуатации open-weight модели

## Допущения

1. Допустимость выделенного контура провайдера для документов с банковской тайной подтвердит DPO
2. Доля полей, присутствующих в документах явно, достаточна для эффекта - проверяется на диагностическом наборе
3. Эталон сотрудника пригоден как разметка при фиксации правил исправления и разборе спорных случаев.

## Риски

| Риск | Митигация |
|---|---|
| Провайдер хранит и использует данные банка | Договорные запреты, аудит, минимизация/обезличивание отправляемых данных |
| Галлюцинации LLM в полях | Ссылка на источник обязательна, поле без источника отклоняется кодом |
| Качество проседает на плохих сканах | Отдельное OCR-звено с локальной калибровкой |
| Цена запросов на реальном объеме выше расчета | Замер расхода на пилоте, порог пересмотра (факт > 2x расчета) -> ускорение self-hosted |

## Триггеры пересмотра

1. Одобрение DPO получено и целевые метрики на приемочном наборе достигнуты -> перевод на self-hosted open-weight в контуре банка
2. Фактическая цена запросов пилота > 2x от расчетной -> досрочный переход на self-hosted
3. Смена версии/лицензии модели провайдера -> регрессионный прогон диагностического набора до обновления
4. Появление нового формата документов в потоке -> расширение приемочного набора и переоценка

## План выхода от вендора

Extraction Service - единая точка с фиксированным интерфейсом (документ -> JSON полей с источниками).
Смена провайдера или переезд на self-hosted - замена адаптера без изменения конвейера, целевой срок миграции - один квартал.
Триггеры выхода: нарушение договорных ограничений, рост цены, смена лицензии, отказ провайдера от закрепления версии
