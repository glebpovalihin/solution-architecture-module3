# Паспорт инициативы: Автоматически выявлять подозрительные операции по счетам

## 1. Триаж

- **Вход -> выход:** поток операций -> приоритетная очередь на проверку (транзит, обналичивание, дробление платежей под пороги)
- **Какое действие изменится:** порядок ручного разбора финмониторинга; вердикт и блокировка за человеком
- **Где именно ML / чем закрыть остальное:** ML-ранжирование по поведению; обязательные к разбору правила кодом
- **Чего не хватает / допущения:** выборка проверок смещена правилами отбора
- **Вердикт:** ML-кандидат

## 2. Постановка

- **Бизнес-цель:** изменить порядок ручного разбора помеченных операций, финмониторинг не успевает разбирать все операции - очередь растет; снижение пропуска фрода и ложных приостановок
- **Объект решения:** отдельная операция по счету
- **Входные данные:** строка таблицы операции, поведенческие агрегаты по клиенту за временные окна, текст назначения платежа в свободной форме; вспомогательно могут быть подключены проверки платформы "Знай своего клиента"
- **Операция:** упорядочить варианты - ранжировать операции по приоритету проверки
- **Результат модели:** скор приоритета 0..1, ранг в очереди
- **Результат для бизнеса:** если не совпадает с результатом модели, то нужна дополнительная обработка - срез топ-N под дневную емкость разбора сотрудниками, детерминированные правила валидации
- **Дальнейшее действие:** сотрудник финмониторинга разбирает операции в порядке очереди и по установленной процедуре решает закрыть или эскалировать на расследование.
- **Источник правильного ответа:** решения сотрудников по приоритетной очереди, зафиксированные по гайдлайну; постоянная вероятностная контрольная выборка из непроверяемой части потока размеченная экспертами; результаты и кейсы пропущенного фрода
- **Роль правил и человека:** правила - расчет признаков, обязательный отбор; человек - все решения, затрагивающие клиента (эскалация, приостановка, отказ в проведении)
- **Открытые вопросы и предположения:** состав допустимых данных требует участия DPO
