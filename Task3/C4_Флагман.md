# C4. Автоматически выявлять подозрительные операции по счетам (Container + Component)

## 1. Container

```plantuml
@startuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml

LAYOUT_TOP_DOWN()
title C4 Container - Сервис приоритизации проверки операций

    Container(ingest, "Ingestion Service", "Go/Rust", "Забирает операции, срабатывания правил")
    ContainerDb(fstore, "Feature Store", "PostgreSQL, Spark", "Поведенческие агрегаты клиента")
    Container(scor, "Scoring Service", "Python, CatBoost", "Скор приоритета")
    Container(nlp, "Text Feature Service", "Python, локальная embedding-модель", "Признаки из назначения платежа")
    Container(prio, "Prioritization Service", "Go/Rust", "Формирует очередь топ-k под емкость разбора, применяет бизнес правила")
    Container(casui, "Case UI", "Web", "Очередь, карточка операции, фиксация решения")
    ContainerDb(labeldb, "Label Store", "PostgreSQL", "Метки очереди и контрольной выборки, исходы расследований")
    Container(mlops, "Registry", "", "Версии моделей, метрики")
    Container(mon, "Monitoring", "Prometheus + Grafana", "Очередь, бизнес-метрики")
}

Rel(abs, ingest, "Операции")
Rel(rules, ingest, "Срабатывания правил")
Rel(kyc, ingest, "Сигнал уровня риска")

Rel(nlp, scor, "Текстовые признаки")
Rel(ingest, nlp, "Назначение платежа")
Rel(scor, prio, "Скор + объяснение")
Rel(rules, prio, "Fallback: очередь по правилам")
Rel(prio, casui, "Топ-k очередь")
Rel(analyst, casui, "Разбор, решение, эскалация")
Rel(casui, labeldb, "Решения разборщика")
Rel(expert, casui, "Разметка контрольной выборки")
Rel(casui, labeldb, "Метки экспертов")
```

## 2. Component

```plantuml
@startuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Component.puml

LAYOUT_TOP_DOWN()
title C4 Component - Scoring и Prioritization

Container_Boundary(scoring, "Scoring Service") {
    Component(validator, "Input Validator", "код", "Схема входа, полнота и свежесть признаков")
    Component(model, "Priority Model", "CatBoost", "Скор приоритета 0..1")
    Component(anomaly, "Anomaly Signal", "IsolationForest", "Признак аномальности")
    Component(calibrator, "Calibrator", "код", "Калибровка скора, объединение с сигналом аномальности")
    Component(fallback, "Fallback Decider", "код", "Наблюдаемые признаки отказа для перехода в резервный путь")
}

Container_Boundary(prio, "Prioritization Service") {
    Component(ranker, "Queue Ranker", "код", "Ранг по калиброванному скору, выбор топ-k")
    Component(bizrules, "Business Rules Guard", "код", "Детерминированные правила обязательных к разбору")
    Component(api, "Output Contract", "JSON", "score, rank, reasons, flags, model_version")
}

ContainerDb_Ext(fstore, "Feature Store", "")
Container_Ext(rules, "Движок пороговых правил", "")
Container_Ext(casui, "Case UI", "")
Container_Ext(mon, "Monitoring", "")

Rel(fstore, validator, "Вектор признаков")
Rel(validator, model, "валидно")
Rel(validator, fallback, "невалидно")
Rel(model, calibrator, "скор")
Rel(anomaly, calibrator, "сигнал аномальности")
Rel(calibrator, ranker, "калиброванный скор")
Rel(ranker, bizrules, "топ-k кандидаты")
Rel(rules, bizrules, "Срабатывания правил")
Rel(fallback, bizrules, "fallback-очередь по правилам")
Rel(bizrules, api, "итоговая очередь")
Rel(api, casui, "Выходной контракт")
Rel(scoring, mon, "Метрики, отказы")
@enduml
```

## 3. Решения

### Границы компонентов
- Обычный код: ingestion, feature store, валидация входа, калибровка/пороги, ранжирование очереди, бизнес-правила, UI, мониторинг
- Модель: только Priority Model (бустинг), Anomaly Signal (вспомогательная), локальная embedding-модель для назначения платежа в качестве генератора признаков
- Очередь: Prioritization Service -> Case UI (топ-k под дневную емкость).
- Человек: разборщик и эксперт встроены в существующий процесс финмониторинга - Case UI и процедура эскалации по правилам внутреннего контроля

Поток обработки: валидация входа -> скор -> калибровка -> ранжирование топ-k -> детерминированные бизнес-правила -> выходной контракт -> Case UI. Rank присваивается после ранжирования.

### Режим обработки
Пакетный скоринг + асинхронная очередь.
Операции скорятся батчами каждые 15 мин.
Последствия: задержка до 15 мин на попадание в очередь является приемлемой,  повторы идемпотентны по operation_id (ключ дедупликации в очереди), человек работает с очередью а не ждет синхронного ответа - падение скоринга не останавливает разбор так как есть фолбек.

### Выходной контракт

```json
{
  "operation_id": "string",
  "score": "number, 0..1",
  "rank": "integer",
  "decision_support": {
    "reasons": [{"feature": "string", "contribution": "number"}],
    "rule_signals": ["string"],
    "kyc_risk_level": "string"
  },
  "flags": ["string"],
  "model_version": "string",
  "scored_at": "string (ISO 8601)"
}
```

### Уровень автоматизации
- Модель только рекомендует порядок разбора и подсвечивает причины.
- Подтверждение человека обязательно для эскалации, приостановки, отказа в проведении
- Автоматически выполняется расчет признаков, ранжирование, формирование очереди, отбор контрольной выборки

### Фолбэк

| Признак | Действие |
|---|---|
| Отсутствие/устаревание признаков | обработка через фолбек (приоритет человеку) |
| Значение за пределами обучающего диапазона | обработка через фолбек (приоритет человеку) |
| Расхождение с сигналом правила | операция остается в очереди |
| Недоступность модели/feature store | обработка через фолбек |
| Превышение лимитов/таймаут скоринга | батч повторяется, затем обработка через фолбек |

### Мониторинг

| Сигнал | Порог | Реакция | Ответственный |
|---|---|---|---|
| Вход: доля пропусков полей, объем потока | Отклонение от обычного диапазона | Триггер переобучения | ML-команда |
| Модель: распределение скоров, доля флагов fallback, версия | Резкая смена распределения | Откат на прошлую версию | ML-команда |
| Очередь человека: длина очереди, время разбора, доля эскалаций в топ-k | Доля эскалаций ниже базовой | Регрессионный запуск и пересмотр | Руководитель финмониторинга |
| Бизнес-метрика: доля ложных приостановок, жалобы | Рост против текущего процесса | Откат порога/модели | Владелец продукта |

## 4. Таблица ответственности компонентов

| Компонент / очередь | Владелец | Допустимое время ожидания | Что при превышении | Кто получает сигнал |
|---|---|---|---|---|
| Ingestion / Feature Store | команда данных | Лаг признаков <= 24 ч | Операции уходят в fallback-очередь по правилам | Дежурный команды |
| Scoring Service | ML-команда | Батч - 15 мин | Повтор батча, затем fallback на правила | ML-команда, владелец сервиса |
| Очередь разбора (Case UI) | Руководитель финмониторинга | Разбор топ-k за рабочий день | Приоритет поднимается, просроченные - в недельный отчет | Руководитель финмониторинга |

## 5. Границы доверия

|Граница | Угроза | Что делаем |
|---|---|---|
| операции -> Ingestion | Недоверенный контент клиента в назначении платежа| Текст обрабатывается только embedding-моделью без исполнения инструкций |
| Знай своего клиента -> Ingestion | Внешний сигнал как факт | Сигнал только признак с пометкой источника, итоговая оценка на стороне банка |
| Scoring -> Case UI | Вероятность полного доверия разборщика скору | обучение персонала, тестирование на специализированных выборках |
